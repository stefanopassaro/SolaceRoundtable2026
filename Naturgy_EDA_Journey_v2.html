If I take you back to where we started, our integration landscape was basically a web of point-to-point, file-based connections. We had more than eighty interfaces talking to around fifteen non-core systems And every single one of those conversations happened the old way: file transfers, MQ queues, periodic batch jobs, huge files moving through a corporate file system overnight. It worked, in the sense that the lights stayed on. But it was fragile and it was slow. There were no REST APIs, no web services, certainly no event-driven anything. Everything was tightly coupled and everything was on-premise. The honest reason we had to change wasn't "the technology is old." It was that this architecture couldn't give the business what it was starting to ask for: near real-time feedback, decoupling so one system going down didn't drag others with it, and the ability to add a new consumer of data without re-engineering a file interface from scratch every time. Batch and point-to-point file transfer simply don't scale to that. So the "why" was really about coupling and latency along with a businesss process scattered in several applications.

The first move was the obvious one, and I think a lot of people make it. We said: let's get rid of the FTP-and-file world and shift to a proper service architecture. So we stood up an API layer — REST APIs, an API management capability to govern and publish them, and an integration layer to transform payloads. We exposed data from our core backend out to the cloud and started publishing web services that our own systems, our providers and our partners could consume. And it felt great at first. Suddenly we had online feedback instead of waiting for a batch. You'd create a work order and it would appear in the commercial system or the mobile app almost immediately, instead of tomorrow morning. So naturally we got enthusiastic and started publishing APIs for everything — commercial, GIS, mobile, you name it.

So naturally we got enthusiastic and started publishing APIs for everything — commercial, GIS, mobile, you name it.But — and this is the important part — we learned fairly quickly that the API was not a magic wand either. Syncing one work order to the mobile app through an API is lovely. But what happens when a batch process generates ten thousand work orders? Or a hundred thousand? Does it really make sense to have a synchronous API suddenly trying to push a hundred thousand objects, with everyone waiting on the other end? That's when it clicked for us that we'd been forcing a synchronous tool onto processes that are fundamentally asynchronous. And when we looked honestly, the vast majority of our processes are asynchronous: you fire a request, the backend does its work, and at some point a result comes back — you want it quickly, but you do not want the caller blocked while it happens.

The first is the field workforce. We generate work orders — and I mean at volume, ten thousand at a time — that have to reach the mobile app our technicians use out on the network in near real time, so they can go and do the job on the asset. Picture trying to do that synchronously: the backend sitting there, waiting for the mobile platform to acknowledge ten thousand creations one after another. It's absurd. With an event-driven approach, each order is just an event published to a topic; the mobile platform consumes from its queue at its own pace, and nobody is blocked. The two systems are completely decoupled, and the field worker still gets their orders within seconds.

That’s just a single request from the customer, but behind it there's a chain of steps across completely different backends. We have to create the work order, create the customer in the corporate system, replicate that customer into the asset-management system, set up the analytical structure to settle the cost, then issue a sales order, generate the invoice, produce the PDF and send it back to the portal. Can you imagine building one synchronous API that does all of that while the customer stares at a spinner? It doesn't exist, and it shouldn't. Instead we publish an event and orchestrate the whole flow through queues and topics — each backend picks up its part, does its work, and emits the next event. The customer gets an acknowledgement immediately, and the choreography happens behind the scenes.

The project I'm most excited about for the next couple of years is the massive rollout of gas smart meters to our 5.5 million customers. This is a big deal in Spain specifically, because for gas we still largely have mechanical meters — automated remote reading at this scale is genuinely new territory for us. This is where the architecture gets interesting, because it's not just an integration challenge, it's a cybersecurity and network-topology challenge. When you bring millions of field devices online, you absolutely cannot have your operational technology network — the OT side, where the meters live — sitting directly exposed to your IT network where the commercial and billing systems run. They have to be physically separated, with serious extra security measures around that boundary. And here's the elegant part: the broker can be installed almost anywhere. It runs in the cloud, which is mostly what we're doing today, but it also runs on-premise, and crucially it can be used to physically separate networks. So the design is to put one broker inside the OT network, right next to the smart meters, collecting the readings as events. Then we have a second broker in the IT network, where the commercial system consumes those readings to bill the customer. A single meter reading becomes an event landing on a queue in the OT broker, and a private, peer-to-peer link between the two brokers carries it across — without there ever being direct physical access between OT and IT. So we get the best of both worlds: real-time-ish meter data flowing into billing, and a hard, broker-mediated boundary protecting the operational network. The same event-driven primitive we use for work orders becomes a security control. That's the kind of reuse that tells you you've picked the right foundation.
